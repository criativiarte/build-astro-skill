# Adotar o Astro CMS Template

Use o manifesto, lockfile, configuração e código do starter empacotado para verificar os contratos abaixo. A estrutura inclui Sveltia CMS e publicação estática. Páginas e seções são compostas em Astro, com os dados editoriais vindos das coleções quando fizer sentido.

## Organizar os arquivos como no template

- Componha as rotas em `src/pages/` com o layout compartilhado de `src/layouts/`. Escreva as seções simples e exclusivas na própria página e extraia componentes quando houver repetição ou responsabilidade clara. Agrupe componentes extraídos em `src/components/` por função ou domínio, como `layout/`, `seo/` e `posts/`. Use o mesmo padrão para novos domínios, como `projects/` em um portfólio.
- Coloque imagens e SVGs processados em `src/assets/`, conteúdo editorial em `src/content/`, utilitários tipados em `src/utils/` e estilos compartilhados em `src/styles/`. Mantenha a configuração pública do CMS em `public/admin/config.yml` e o schema no arquivo `src/content.config.ts`. Siga os nomes, aliases e a composição de componentes usados na base empacotada.

## Aproveitar a fundação

- Preserve o modo estático, npm, `package-lock.json`, os scripts e o Node exigido pelo `package.json`. Use `npm ci --include=dev` no destino com lockfile compatível. TypeScript, checker, coleções Iconify e ferramentas usadas no build podem estar em `devDependencies`. As fontes podem exigir acesso ao provedor no primeiro build sem cache.
- Use `src/layouts/Layout.astro` para conectar cabeçalho, rodapé, slots, fontes e SEO. Reaproveite `src/components/seo/Head.astro` e suas props para metadados por página. Use `src/consts.ts` para identidade padrão e `astro.config.mjs` para o domínio público.
- Use o alias `@/` e reaproveite `Container.astro`, tokens, classes de títulos e botões em `src/styles/global.css`. O container desta base usa `.site-container` com `w-9/10 max-w-site`. Preserve a grade existente enquanto ela atender ao design. Mantenha estilos editoriais em `post.css`. Para trocar fontes, sincronize `astro.config.mjs`, os componentes `Font` no layout e os aliases `@theme inline`. Reutilize os ícones `lucide:` já instalados e faça a exportação de SVGs próprios para `src/assets/icons/` quando necessário.

## Modelar o conteúdo do site

- Percorra os frames e as rotas para inventariar conteúdo editorial antes de montar as páginas. Anote, para cada candidato, quem provavelmente o atualiza, quais operações precisa fazer sem editar código (criar, editar, ordenar ou despublicar) e onde o dado aparece. Use o propósito do site, o Figma e o CMS existente como evidência. Resolva casos reversíveis sem questionário adicional. Em adaptações, confirme mudanças que afetem rotas, dados existentes ou responsabilidades.
- Procure o mesmo dado em contextos diferentes, como contato no rodapé e no CTA ou projeto na home e no detalhe. Use uma única fonte de dados para esses consumidores. Uma única ocorrência, como um evento representativo de uma agenda, pode indicar uma coleção. Cards iguais não são evidência suficiente de edição: compartilhe o componente, mas deixe em Astro o conteúdo fixo que não tem rotina editorial. Mantenha estrutura, estilos e comportamento fora do CMS.
- Escolha o formato mais simples que preserve a rotina editorial. Use um singleton em JSON para dados únicos editáveis, como os contatos de atendimento. Use uma coleção de arquivo único em JSON para uma lista pequena e estruturada, como horários ou depoimentos. Use uma coleção de pasta com uma entrada por arquivo para conteúdo independente, como projetos, serviços ou eventos que tenham corpo editorial ou página própria. Adicione relações apenas quando os itens forem compartilhados e gerenciados separadamente. Use Markdown para texto longo quando for o formato adequado.
- Para um site novo sem blog, retire juntos as rotas em `src/pages/posts/`, componentes exclusivos em `src/components/posts/`, helpers tipados em `src/utils/posts.ts`, a coleção Astro `posts` e seus dados de exemplo. Remova ou reaproveite autores e tags só após conferir consumidores. Atualize os links da home e do cabeçalho. No CMS, ajuste as coleções, previews e caminhos globais de mídia que apontam para posts. Preserve os singletons ainda lidos pelo layout. Em um site existente, preserve o conteúdo e as rotas em uso, salvo migração ou remoção solicitada.
- Para outros formatos, adapte o padrão de listagem, detalhe e arquivos por categoria conforme necessário. Gere rotas estáticas com `getStaticPaths()` quando houver páginas individuais. Mantenha identificadores estáveis após mudança de título. Use status, filtros, datas e ordenação quando fizerem parte da publicação daquele conteúdo.

## Implementar coleções no padrão da base

- Mantenha alinhados o schema de `src/content.config.ts`, os campos de `public/admin/config.yml` e os arquivos em `src/content/`. Preserve o fluxo de edição via Git em `/admin/`. O repositório, a branch, o domínio, o título e o logo do painel são configuração pública. Credenciais são fornecidas pelo responsável na autenticação do CMS.
- Reaproveite os loaders `glob()` ou `file()` usados pela base para o formato escolhido, com schema em `astro/zod` e consultas tipadas em `astro:content`. Espelhe no painel e no build os campos obrigatórios, valores opcionais, padrões e validações. Quando houver regras de seleção ou ordenação, centralize-as em utilitários tipados compartilhados pelas rotas e componentes. Preserve a geração estática.
- Se houver blog, use `getPublishedPosts()`, `getPostData()` e os utilitários de tags de `src/utils/posts.ts`. Preserve a ordenação de publicação, a exclusão de rascunhos de páginas e arquivos públicos e o `post.id` como slug de `/posts/<slug>/`. Mantenha as relações por nome no frontmatter das coleções atuais e revise entradas afetadas se um nome mudar.
- Para mídia editorial, alinhe a pasta de upload, o caminho persistido pelo CMS e a resolução do asset no schema do Astro. Siga o padrão de `src/assets/images/posts/` para as capas de posts e use pastas equivalentes para outros acervos quando necessário. Trate imagens opcionais na apresentação e preserve os caminhos de mídias existentes.

## Preparar e verificar a entrega

- Use a identidade do projeto em `src/consts.ts`, nos assets e no `app_title` e logo do CMS. Alinhe `site` do Astro ao domínio público confirmado. No CMS, defina `site_url` quando precisar indicar uma origem explícita. Só use `display_url` se “Ver site” precisar apontar para um destino diferente. Sem domínio confirmado, omita os dois no preview em que painel e site compartilham origem; o Sveltia usa a origem do painel por padrão. Se o Astro exigir `site` para o build, use a origem real do preview local, sem aprovar essa saída para publicação. [URLs no Sveltia CMS](https://sveltiacms.app/en/docs/customization#site-url)
- Configure `backend.repo` e `branch` com valores confirmados. Sem eles, mantenha a modelagem e registre a conexão editorial como pendente, sem publicar configuração de login demonstrativa. A presença de `/admin/` no build não comprova edição ou publicação pelo CMS. Se faltar telefone real, mantenha o WhatsApp desativado.
- Preserve o estado `enabled` dos scripts existentes. Nos sites novos, remova as entradas demonstrativas do starter. Habilite um rastreador novo somente quando sua configuração fizer parte do pedido. Até que haja uma política publicável, os scripts já marcados como ativos carregam com `requireConsent={false}`. Quando a configuração tornar a política publicável, o layout passa a exigir consentimento. Verifique aceite, recusa e revogação quando esse fluxo estiver no escopo. A lista de serviços da política serve para exibição e não altera o estado dos scripts.
- Execute `npm run check`, `npm run build` e confira o preview local. Valide com dados representativos cada coleção alterada, incluindo uma imagem real de teste quando o schema aceitar mídia. Confira as rotas, links, canonical, metadados, `robots.txt`, sitemap e `llms*.txt`. Sem blog, verifique a ausência de rotas, links e entradas do blog nessas saídas. Confira também a exclusão de rascunhos e de `/admin/` dos índices. O starter usa as convenções de saída estática em `dist/`, rotas em diretórios e `base` na raiz. Revise os links e os hooks de sitemap e `llms` se o deploy exigir outros caminhos.
- Use a saída estática de `dist/` para publicar quando o desenvolvedor solicitar deploy e fornecer o destino. Reaproveite a infraestrutura do projeto existente quando estiver configurada. Em sites novos, a configuração de deploy fica para a hospedagem escolhida.
